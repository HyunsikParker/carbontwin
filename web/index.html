Track: Carbon Markets & Emissions Transparency

One project, two registries, the same vintage issued twice?

CarbonTwin screens every listing in Berkeley's database of the major voluntary carbon registries, asks an open-weight model running locally whether two listings describe the same physical asset, and records the answer in a smart contract that refuses a second registry's issuance for a vintage that was already issued.

  1. ScreenTF-IDF name matching, developer, site and type checks across … listings
  2. AdjudicateGemma 4 12B, run locally at temperature 0, reads both records and returns a JSON verdict with a reason
  3. AnchorEach finding is hashed into a Merkle tree; the root is stored on-chain
  4. EnforceLinked listings share one asset key, so a second registry cannot issue the same vintage

Findings

A finding means the adjudicator judged both listings to be the same asset and both registries issued credits for at least one common vintage. Registry transfers can legitimately split a vintage, so each finding is a reconciliation question for the registries, not a verdict of double counting.

Method and limits

Data

Vintage issuance per listing comes from the registries' public records as compiled by Berkeley. Serial numbers are not in the summary data, so overlap is measured per vintage, using the smaller of the two issuances.

Matching and adjudication

Pairs are candidates when names are similar within the same country (character n-gram TF-IDF, cosine ≥ 0.62). The model sees name, developer, site, type, methodology, status, vintage profile, notes and description for both listings. Phases, different capacities and different sites are told to count as different assets.

What the contract adds

Registries keep their own systems. They post issuance claims keyed by listing and vintage. Once an auditor links two listings, they share an asset key: past overlaps become events anyone can see, and future overlaps revert with DoubleIssuance.
